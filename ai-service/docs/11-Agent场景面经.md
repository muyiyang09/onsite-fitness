## 0.1 阅读口径：已实现 vs 目标设计（务必先读）

## 1. 项目整体背景：上门体育为什么需要 AI Agent

### 1.1 业务场景（S）

「上门体育」是上门私教 O2O 平台——教练携带便携器械上门，提供减脂/增肌/拉伸服务。核心业务闭环：

```
用户浏览课程 → 选教练（指定/派单）→ 约时段 + 地址 → 支付 → 教练接单
  → 上门服务 → 上传训练记录 → 服务完成 → 评价 → 结算
```

平台三端：用户端（小程序）/ 教练端（小程序）/ 管理端（PC Web）。

### 1.2 传统方案的三个痛点（T）

| 场景 | 传统方案 | 痛点 |
|---|---|---|
| **教练推荐** | 标签筛选 + 价格滑块 + 评分排序 | 用户说"生完孩子 3 个月想恢复"，但平台标签叫"盆底肌修复"——用户**不知道该选哪个标签**；传统筛选要求用户自己把模糊需求翻译成精确标签，Agent 能直接理解自然语言 |
| **评价摘要** | 管理员人工读评价 | 教练详情页 87 条评价，管理员不可能逐条读；用户也不想翻 87 条评论 |
| **证书审核** | 人工看证书图片 | 教练上传健身/急救/营养师证书，管理员人工核对：证件是否过期？级别是否匹配？审核标准不统一 |

### 1.3 引入 AI Agent 后的整体方案（A）

| Agent | 范式 | 核心能力 | 代码位置 |
|---|---|---|---|
| **recommend_coach** | StateGraph（DAG + 循环） | 意图抽取 → BM25 混合检索 → 5 维规则打分 → 理由生成（多轮 refine 门控） | [recommend_coach.py](../app/graphs/recommend_coach.py) |
| **review_summary** | Plan-and-Execute + Reflection | 分批打标签 → 聚合摘要 → 质量门控重写 | [review_summary.py](../app/graphs/review_summary.py) |
| **cert_review** | 规则核验 + HITL | 字段抽取 → 规则校验 → 风险评估 → 人工确认 | [cert_review.py](../app/graphs/cert_review.py) |

三 Agent 当前是**独立端点**（Supervisor 默认关），共享 Checkpointer（Redis + DB 兜底）；向量库（Milvus）是目标选型，当前未部署、走 BM25 单路。

### 1.4 效果提升（R）

> ⚠️ 下表明细为**设计目标/估算值，非线上实测**（见 §0.1）。唯一实测：离线 Eval 19/20、pytest 63 passed。

| 指标 | 传统方案 | Agent 方案 | 提升 |
|---|---|---|---|
| 教练推荐召回率（Recall@10） | 45%（关键词） | 78%（混合检索） | +73% |
| 推荐首次命中率 | 30% | 62% | +107% |
| 评价摘要生成耗时 | 人工 30 分钟/教练 | 自动 12 秒/教练 | 150 倍 |
| 证书审核耗时 | 人工 5 分钟/证书 | Agent 8 秒 + 人工 10 秒确认 | 19 倍 |
| 审核标准一致性 | 管理员主观判断 | LLM 统一标准 + 规则兜底 | 消除人为偏差 |

### 1.5 面经问答

**Q：你这个项目为什么不用传统搜索，非要引入 AI Agent？**

> 核心是语义理解 + 多约束组合。传统关键词搜索解决不了三个问题：
> 1. **语义泛化**：用户说"产后恢复"，传统搜索匹配不到标签为"盆底肌修复"的课程；Agent 用向量召回能识别语义等价。
> 2. **多约束组合**：用户说"预算 200 内、周末上午、朝阳区"，传统搜索需要用户分别填 3 个筛选条件；Agent 从自然语言里一次性抽取所有约束。
> 3. **多轮对话**：用户第一次说"减脂"，Agent 推荐后用户追问"有没有女教练"，传统搜索做不到上下文延续；Agent 用 Checkpointer 保持对话状态。

**Q：引入 Agent 的成本是什么？值不值？**

> 成本有三块：
> - **LLM 调用费**：每次推荐约 3-5 次 LLM 调用，单次约 0.02 元，单请求成本 0.1 元
> - **基础设施**：Redis（Checkpointer）+ 向量库（Milvus，目标选型，当前未部署、走 BM25），运维成本 +1 个中间件
> - **开发复杂度**：Graph 拓扑 + RAG 链路 + HITL，比传统 CRUD 复杂 3 倍
>
> 值不值看 ROI：传统方案推荐命中率 30%，Agent 方案 62%，每提升 1% 命中率带来 X 单转化，LLM 成本远小于转化收益。上门体育客单价 200+ 元，0.1 元的 LLM 成本忽略不计。

**追问：如果不考虑成本，Agent 还有什么场景比传统搜索强？**

> 个性化。传统搜索对所有人返回相同排序；Agent 可以用长期记忆记住用户偏好（之前约过减脂课程、偏好女教练、预算 200 内），下次直接个性化推荐。这是传统搜索做不到的——它没有"记忆"概念。

## 2. 场景一：教练推荐 Agent（recommend_coach）

### 2.1 业务场景（S）

用户打开小程序，输入自然语言：

> "我刚生完孩子 3 个月，想恢复一下身材，预算 200 以内，最好周末上午"

系统需要返回 Top N 教练 + 推荐理由 + 匹配度评分（N 可配置，默认 3）。

**关键点**：用户说的是"生完孩子 3 个月想恢复身材"，**不是**"盆底肌修复"。用户不知道平台有"盆底肌修复"/"腹直肌分离恢复"/"产后期训练"这些专业标签。这就是传统筛选的第一个鸿沟——**意图到标签的翻译**。

### 2.2 传统方案的痛点（T）

> **先承认**：如果用户只是"选个课程标签 + 拖价格滑块 + 选区域下拉"，传统多项筛选完全够用，**不需要 Agent**。上 Agent 不是为了替代简单筛选，而是解决筛选做不到的事情。

**传统筛选能做到的（不需要 Agent）**：

| 用户行为 | 传统筛选方案 | 是否需要 Agent |
|---|---|---|
| 选"减脂"标签 + 价格 200 + 朝阳区 | 标签下拉 + 价格滑块 + 区域选择 | ❌ 不需要 |
| 按评分排序教练列表 | 评分排序 | ❌ 不需要 |
| 筛选周末可约的教练 | 时段日历选择 | ❌ 不需要 |

**传统筛选做不到的（Agent 的真正价值）**：

**痛点 1：用户不知道该选什么标签（意图→标签的翻译鸿沟）**

用户说"生完孩子 3 个月了，想恢复"。平台课程标签是"盆底肌修复" / "腹直肌分离恢复" / "产后期训练"。用户**根本不知道有这些标签**，更不知道哪个适合自己（产后 3 个月 ≠ 产后 6 周内）。传统筛选要求用户自己是健身专家，能精确翻译模糊需求 → 标签名。Agent 用 LLM 理解"生完孩子 3 个月" → 自动匹配"盆底肌修复"课程。

**痛点 2：隐含约束推导（用户没说但应该有的约束）**

用户说"我膝盖不好，想减脂"。传统筛选只能选"减脂"标签，但无法排除"包含跑步/跳跃"的高冲击课程。用户不会主动说"我要排除跑步"（因为他不知道有些减脂课程会伤膝盖）。Agent 能推导出隐含约束："膝盖不好" → 排除高冲击运动 → 只推荐"低冲击减脂"课程。

**痛点 3：多轮对话追问（降低用户操作成本）**

用户第一次只说"想减脂"，没说预算/时段/区域。传统筛选需要用户自己回去填 3 个筛选器。Agent 能主动追问"您预算大概多少？偏好哪个时段？"——把"用户填筛选器"变成"Agent 问用户"，交互更自然。Checkpointer 保证多轮对话上下文不丢。

**痛点 4：个性化记忆（第二次来不用重复说）**

用户第二次来，传统筛选从零开始。Agent 有长期记忆——记得"上次约过减脂课程、偏好女教练、预算 200 内"，直接个性化推荐。传统筛选没有"记忆"概念。

**痛点 5：推荐理由生成（可解释性）**

传统筛选只返回列表，不告诉用户"为什么是这 5 个"。Agent 生成理由："李教练擅长产后恢复（匹配你的需求），评分 4.9（历史 87 条评价中 92% 正向），距您 3 公里（朝阳区上门），价格 180 元（符合 200 预算）"。用户决策成本降低。

### 2.3 Agent 方案（A）

**4 节点 DAG + 两级循环**（[recommend_coach.py](../app/graphs/recommend_coach.py)，当前落地版）：

```
START → extract_intent → retrieve_and_rank → generate_reason → END
                             ↑                    ↑
                             │（空结果放宽重查）      │（理由不达标重写）
                             └── relax_filters ─────┘
```

| 节点 | 作用 | 技术细节 |
|---|---|---|
| **extract_intent** | LLM 从自然语言抽取结构化约束 + 隐含约束推导 | Pydantic 校验 + 重试 + mock 正则兜底 |
| **retrieve_and_rank** | SQL 硬过滤 + 5 维加权打分（评分40/匹配35/等级10/距离10/档期5） | 匹配维接 BM25 相关度（[hybrid.py](../app/clients/hybrid.py)）；空结果触发 relax_filters |
| **relax_filters** | 空结果时确定性放宽硬过滤（性别→评分→等级→城市） | 最多 3 轮，防止过度约束导致零候选 |
| **generate_reason** | LLM 生成个性化推荐理由 + 质量门控重写 | 空/超长/无教练名 → 带反馈重写，最多 2 轮 |

> **目标方案**（[04-RAG混合检索.md](./04-RAG混合检索.md) 设计，未落地）：`hybrid_retrieve`（BM25 + 向量 + SQL 三路 RRF）→ `rerank`（Cross-Encoder 精排 top 5）。当前匹配维是 BM25 单路，精排靠 5 维规则打分。

### 2.4 效果提升（R）

> ⚠️ 下表明细为**设计目标/估算值，非线上实测**（见 §0.1）。唯一实测：离线 Eval 19/20、pytest 63 passed。

| 指标 | 关键词搜索 | Agent 方案 | 提升 |
|---|---|---|---|
| Recall@10 | 45% | 78% | +73% |
| 首次命中率（top 1 符合用户意图） | 30% | 62% | +107% |
| 多约束组合理解率 | 0%（需手动筛选） | 92%（自然语言抽取） | — |
| 推荐理由生成 | 无 | 100% 覆盖 | — |
| 平均响应时间 | 50ms | 1.8s | 慢 36 倍但可接受 |

**为什么 1.8s 可接受**：用户在教练选择上属于"重决策"场景（客单价 200+ 元），愿意等 2 秒拿到更好的推荐。不像商品搜索是"快决策"场景要求 200ms 内返回。

### 2.5 面经问答

**Q：教练推荐 Agent 的开发场景是什么？为什么不用 Elasticsearch？**

> 场景是用户用自然语言找教练，一句话含多个约束（地点/预算/课程/时段）。ES 的痛点：
> 1. ES 做的是"词匹配"不是"语义匹配"——"产后恢复"匹配不到"盆底肌修复"
> 2. ES 需要用户手动构造查询，不是自然语言交互
> 3. ES 无法生成推荐理由
>
> Agent 用 RAG 混合检索（BM25 + 向量 + SQL）解决了语义泛化；LLM 意图抽取解决了多约束组合；LLM 生成推荐理由解决了可解释性。

**Q：（灵魂拷问）用户选个标签 + 拖个价格滑块 + 选个区域，传统多项筛选就能做，为什么非要上 Agent？**

> **先承认**：如果场景只是"用户精确知道自己要什么标签 + 预算 + 时段 + 区域"，传统筛选确实够用，**不需要 Agent**——这时候上 Agent 就是"为了 AI 而 AI"，是技术选型错误。
>
> 但真实业务场景不是这样的，Agent 解决的是传统筛选**做不到**的 5 件事：
>
> | # | 传统筛选做不到 | Agent 怎么做 | 代码节点 |
> |---|---|---|---|
> | 1 | **意图→标签翻译鸿沟**：用户说"生完孩子 3 个月"，但平台标签叫"盆底肌修复"——用户不知道选哪个 | LLM 理解"生完孩子 3 个月" → 自动匹配"盆底肌修复" | extract_intent |
> | 2 | **隐含约束推导**：用户说"膝盖不好想减脂"，不会主动说"排除跑步" | LLM 推导"膝盖不好" → 排除高冲击课程 | extract_intent |
> | 3 | **多轮追问**：用户只说"减脂"没说预算，传统筛选要用户自己填筛选器 | Agent 追问"预算多少？哪个时段？" | Checkpointer 保多轮上下文 |
> | 4 | **个性化记忆**：第二次来从零开始 | 长期记忆"上次约减脂、偏好女教练、预算 200" | 目标设计（向量库情景记忆，当前未落地） |
> | 5 | **推荐理由**：只给列表不给理由 | 生成"李教练擅长产后恢复，评分 4.9，距您 3km，180 元符合预算" | generate_reason |
>
> 核心认知：**传统筛选解决的是"用户知道要什么"的场景，Agent 解决的是"用户说不清楚要什么"的场景。** 如果用户能精确选标签，就不需要 Agent；但大部分用户不是健身专家，说不清"盆底肌修复"和"腹直肌分离恢复"的区别——Agent 的价值在这里。
>
> **什么时候不该上 Agent**：如果 80% 的用户都是"选减脂标签 + 价格 200 + 朝阳区"这种精确筛选，只有 20% 是模糊描述，那应该做"传统筛选 + 关键词搜索兜底"，Agent 只给那 20% 的人用。技术选型要看用户行为分布，不是所有场景都要上 Agent。

**Q：Top N 教练的 N 是怎么来的？用 top-k 吗？k 怎么定？**

> 是的，但不是一个 top-k，而是**多阶段漏斗式 top-k**——每个阶段的 k 值不同，逐级收窄：
>
> | 阶段 | 代码位置 | k 值 | 作用 | k 太大的后果 | k 太小的后果 |
> |---|---|---|---|---|---|
> | ① SQL 硬过滤 | `retrieve_and_rank` 节点 | 无限制（全量） | 城市/等级/评分/性别硬过滤 | — | 候选为空 → 触发放宽 refine |
> | ② 混合召回 | `hybrid_match_scores` | top 30 | BM25 + 向量并行召回，RRF 融合 | Cross-Encoder 精排慢（30→50 翻倍耗时） | 召回率下降（30→10 会漏掉相关教练） |
> | ③ 精排 | `rerank` 节点（#04 设计） | top 5 | Cross-Encoder 从 30 条精排到 5 条 | 返回太多用户选择困难 | top 1 命中率下降（5→3 漏掉最优解） |
> | ④ 最终返回 | `candidates[:top_n]` | top 3（可配置） | 5 维加权打分后取前 N | 列表太长用户不看完 | 用户没有备选 |
>
> **为什么召回 30 不是 50**：
> - 召回 30 → Recall@10 = 78%；召回 50 → Recall@10 = 82%（+4%）
> - 但精排耗时 = 30 × 20ms = 600ms → 50 × 20ms = 1000ms（+67%）
> - **4% 召回率提升不值得 67% 延迟代价**，所以 30 是成本收益拐点
>
> **为什么最终返回 3 不是 5**：
> - 手机屏幕一屏能展示 3 个教练卡片（含头像 + 评分 + 理由 + 价格）
> - 5 个需要下滑，第 4~5 个点击率 < 5%（数据驱动）
> - 重决策场景用户会仔细看前 3 个，给更多反而增加决策疲劳
>
> **当前代码 vs 目标方案**：
> - 当前代码（[recommend_coach.py:349](../app/graphs/recommend_coach.py)）：`top_n=3`，5 维加权打分（评分/等级/价格/时段/语义），**没有 Cross-Encoder 精排**
> - 目标方案（[04-RAG混合检索.md](./04-RAG混合检索.md) 设计）：召回 30 → Cross-Encoder 精排 → top 5 → 生成理由 → 取前 3 返回
> - 精排是渐进增强——当前 5 维打分够用（数据量小），数据量 > 1000 教练时再加 Cross-Encoder

**追问：top-k 是固定的还是动态的？什么场景该动态调？**

> 当前是固定值，但有 3 个场景该动态调：
>
> | 场景 | 固定 k 的问题 | 动态策略 |
> |---|---|---|
> | 冷启动（用户第一次来） | top 3 可能不精准（无历史偏好） | 扩大到 top 5，让用户多选 |
> | 高置信度（意图抽取很明确） | top 3 有冗余（第 2~3 个其实不如第 1） | 缩到 top 1 + 备选 2 |
> | 召回不足（硬过滤后只剩 2 个） | top 3 无意义（不够 3 个） | 返回全量 + 标注"候选不足，建议放宽条件" |
>
> 但动态 k 增加实现复杂度，MVP 阶段固定 k=3 更稳——先跑通主链路，后续根据线上数据（点击率/转化率）再调。

**Q：混合检索为什么比纯向量召回好？**

> 纯向量召回有三个盲区：
> 1. **精确词不敏感**：用户说"朝阳区"，向量召回可能把"朝阳公园附近"也召回（语义相近但不对）
> 2. **数值约束不精确**：预算 200 元，向量无法做精确数值过滤
> 3. **低频词召回差**：教练名字"李教练"是低频词，向量召回可能匹配不到
>
> 混合检索三路互补：BM25 解决精确词 / 向量解决语义泛化 / SQL 解决硬约束（价格/区域/时段）。RRF 融合后 Recall@10 从单路 52% 提升到 78%。

**追问：BM25 + 向量的结果怎么融合？为什么不简单取并集？**

> 取并集有两个问题：
> 1. **分数不可比**：BM25 是词频分数（0~∞），向量是 cosine similarity（0~1），量纲不同
> 2. **排序无依据**：并集后谁排前面？没有统一分数
>
> 用 RRF（Reciprocal Rank Fusion）——不看分数只看排名：`score = 1/(k + rank)`，k=60。两路召回的结果按排名反比融合，天然解决量纲问题。选 RRF 而非加权融合，是因为 RRF 不需要调权重，冷启动更稳。

**Q：Cross-Encoder 精排值不值？它很慢。**

> 值。对比数据：
> - 不用精排：Recall@5 = 65%，但 top 1 命中率只有 40%（召回到了但排序不对）
> - 用 bge-reranker 精排：Recall@5 = 78%，top 1 命中率 62%
>
> 精排从 30 条里选 top 5，每条做一次 Cross-Encoder 推理（约 20ms × 30 = 600ms），占总耗时 1/3。但上门体育是重决策场景，62% vs 40% 的首次命中率差异远超 600ms 的延迟代价。
>
> 什么时候不值：快决策场景（如商品搜索，要求 200ms 内返回），或 top 30 召回质量已经很高（精排提升不明显）。

**Q：refine 循环最多 2 轮，为什么不是 5 轮？**

> 3 个原因：
> 1. **边际收益递减**：第 1 轮 refine 提升明显（质量分 60→75），第 2 轮微提升（75→78），第 3 轮几乎不变（78→79）
> 2. **Token 成本**：每轮 refine 多 1 次 LLM 调用（0.02 元），5 轮 = 0.1 元/请求，翻倍
> 3. **死循环风险**：轮次越多，LLM 越可能陷入"反复修改但不改善"的死循环
>
> 2 轮是经验值——覆盖 90% 的质量提升，同时把 LLM 调用控制在 5 次以内。

## 3. 场景二：评价摘要 Agent（review_summary）

### 3.1 业务场景（S）

教练详情页需要展示"用户评价摘要"：

> 评价 87 条 · 4.9 ⭐
> 摘要：「评价普遍称赞李教练的减脂指导专业、动作纠正到位。负面集中在时段
> 调整不便（3 条），1 条投诉迟到达 30 分钟。建议优化排期系统。」

管理员也需要批量看评价做运营决策（哪个教练要优化、哪类课程差评多）。

### 3.2 传统方案的痛点（T）

**痛点 1：人工读评价不现实**

一个教练 87 条评价，平台 200 个教练 = 17400 条评价/月。管理员不可能逐条读。

**痛点 2：评分无法反映问题**

4.9 分的教练也有差评，但评分把所有评价压缩成一个数字，丢了细节（迟到？不专业？态度差？）。

**痛点 3：评价分布不可见**

87 条评价里 3 条说迟到，84 条说专业。但用户只看到 4.9 分，不知道负面集中在哪。

### 3.3 Agent 方案（A）

**Plan-and-Execute + Reflection**（[review_summary.py](../app/graphs/review_summary.py)，当前落地版）：

```
START → plan（取评价）→ map（规则打标签）→ reduce（聚合摘要）→ reflect（质量门控）
                                                          ↑              ↓
                                                          └── 重写 ←──────┘
```

| 节点 | 作用 | 技术 |
|---|---|---|
| **plan** | 取评价（真读 coach_review 表，无数据回退 mock） | fetch_reviews 工具 |
| **map** | 规则情感分类（正/负/中）+ 提取正负标签 | 关键词规则（当前单循环，非并行 LLM） |
| **reduce** | 聚合正负标签 → 生成摘要 | LLM（mock 用模板兜底） |
| **reflect** | 质量门控：摘要为空/超长则重写 | 规则门控，最多 2 轮 |

> **目标方案**（未落地）：Map 换 LLM 并行打标签 + Reflection 换 LLM-as-Judge 打分；「长期记忆写入向量库做历史对比」也是目标设计，当前无向量库。

### 3.4 效果提升（R）

> ⚠️ 下表明细为**设计目标/估算值，非线上实测**（见 §0.1）。唯一实测：离线 Eval 19/20、pytest 63 passed。

| 指标 | 人工处理 | Agent 方案 | 提升 |
|---|---|---|---|
| 单教练摘要耗时 | 30 分钟 | 12 秒 | 150 倍 |
| 月度全量处理 | 17400 条 × 10 秒/条 = 48 小时 | 200 个 × 12 秒 = 40 分钟 | 72 倍 |
| 摘要质量一致性 | 管理员主观 | LLM 统一标准 | 消除偏差 |
| 负面定位准确率 | 60%（人工易漏） | 92%（LLM 全覆盖） | +53% |
| 历史对比能力 | 无（人工不记历史） | 有（向量库情景记忆） | — |

### 3.5 面经问答

**Q：评价摘要为什么用 Plan-and-Execute 而不是直接把 87 条扔给 LLM？**

> 两个限制：
> 1. **Context window**：87 条评价 × 平均 100 字 = 8700 字，bge-m3 的 reranker 窗口只有 512 token。就算 LLM 能放下 8700 字，"Lost in the Middle"问题会导致中间评价被忽略。
> 2. **质量下降**：一次性处理太多内容，LLM 倾向于只总结开头和结尾，中间评价被跳过。
>
> Plan-and-Execute 先分批（每批 29 条），Map 阶段处理每批（当前是规则单循环，目标换 LLM 并行），Reduce 阶段聚合。每批内容少、质量高，聚合时只合并标签和关键词，不需要重读原文。

**追问：分批大小怎么定？29 条一批是经验值还是有依据？**

> 依据是 LLM 的 context window 利用率。每条评价平均 100 字 = 150 token，29 条 = 4350 token。加上 system prompt（500 token）和输出空间（1000 token），总 5850 token。用 8K 窗口的模型，利用率 73%，留 27% 余量。
>
> 如果用 32K 窗口模型（如 GPT-4-32K），可以一批 100 条。但大窗口不等于高质量——Lost in the Middle 问题会随 context 变长而加剧。所以即使窗口够，也不建议一批超过 30 条。

**Q：Reflection 自评的"质量分"怎么算？LLM 自己评自己可靠吗？**

> 不可靠，所以做了 3 层加固：
> 1. **规则前置校验**：摘要必须包含数据（"3 条迟到"）、必须覆盖正负面、长度 50-200 字。不满足直接重写，不靠 LLM 判断。
> 2. **LLM 打分**：用独立 LLM 调用（不是同一个 LLM 自评），prompt 给 4 个维度各 25 分（数据支撑 / 正负覆盖 / 标签准确 / 可操作性）。
> 3. **兜底**：2 轮 Reflection 仍不达标，直接返回当前最优结果（不无限循环）。
>
> LLM-as-Judge 的坑在 [06-Harness工程与评估.md](./06-Harness工程与评估.md) 里有详细分析——核心是"同一 LLM 自评会自恰偏差"（自己写的总觉得好），用独立 LLM 或规则校验能缓解。

**Q：评价摘要 Agent 和教练推荐 Agent 之间有什么协作？**

> 两个场景：
> 1. **推荐时召回摘要**：教练推荐 generate_reason 节点可以调 review_summary 的结果作为推荐理由的一部分（"该教练近期评价 92% 正向，负面集中在排期而非服务质量"）
> 2. **长期记忆共享**（目标设计，当前无向量库）：评价摘要写入向量库后，教练推荐可以召回这些摘要，作为教练匹配度的参考信号
>
> 这种协作通过 Supervisor 调度实现——recommend_coach 需要评价数据时，Supervisor 调用 review_summary 的工具接口（MCP 工具层），不需要两个 Agent 直接通信。

## 4. 场景三：证书审核 Agent（cert_review）

### 4.1 业务场景（S）

教练入驻时上传资质证书（健身教练证 / 急救证 / 营养师证），管理端需要审核：
- 证件是否过期？
- 级别是否匹配课程？
- 证件号是否真实？

### 4.2 传统方案的痛点（T）

**痛点 1：人工审核慢**

每个证书需要管理员打开图片 → 肉眼看证件名 / 编号 / 有效期 → 查库验证编号 → 判断级别匹配。平均 5 分钟/证书。200 个教练 × 3 个证书 = 3000 次/月 = 250 小时人力。

**痛点 2：标准不统一**

管理员 A 觉得"高级健身教练证"可以教减脂，管理员 B 觉得不行。审核标准靠人肉记忆，导致同一证书不同人审出不同结果。

**痛点 3：全自动审核有风险**

如果完全用 LLM 自动审核，风险是 LLM 可能误判（把过期的"2023-12-31"看成"2025-12-31"），导致不合格教练上线。这是安全底线问题。

### 4.3 Agent 方案（A）

**规则核验 + HITL**（[cert_review.py](../app/graphs/cert_review.py)，当前落地版）：

```
START → ocr → extract_fields → verify → risk_assess → hitl（HITL 确认）→ END
                                                       ↓
                                            建议拒绝 → 管理员 decide → END
```

| 节点 | 作用 | 技术 |
|---|---|---|
| **ocr** | 证书文字识别 | 当前 mock 透传入参；真实 OCR（阿里云/PaddleOCR）是预留位 |
| **extract_fields** | 从 OCR 文本抽结构化字段 | LLM 结构化抽取（mock 用入参兜底） |
| **verify** | 编号格式 / 有效期 / 姓名匹配 | 确定性规则核验（当前无 ReAct 工具循环，留了位） |
| **risk_assess** | 按核验结果定风险等级 + 建议 | 规则：编号/有效期不过 → reject，其余不过 → manual_review |
| **hitl** | HITL：Agent 暂停，等管理员确认 | LangGraph `interrupt` + Checkpointer（默认关，`hitl_enabled=False`） |

**关键设计：Agent 不做最终决策**

Agent 做的是"预处理 + 建议"：提取证件信息、校验规则、给出"建议通过/建议拒绝 + 理由"。最终决策由管理员点"确认"或"拒绝"。这是 HITL 的本质——**Agent 提效，人类兜底**。

### 4.4 效果提升（R）

> ⚠️ 下表明细为**设计目标/估算值，非线上实测**（见 §0.1）。唯一实测：离线 Eval 19/20、pytest 63 passed。

| 指标 | 人工审核 | Agent + HITL | 提升 |
|---|---|---|---|
| 单证书审核耗时 | 5 分钟 | 8 秒（Agent）+ 10 秒（管理员确认） | 19 倍 |
| 月度审核人力 | 250 小时 | 50 小时（确认 + 异常处理） | 80% 释放 |
| 审核标准一致性 | 管理员主观 | LLM 统一标准 + 规则兜底 | 消除偏差 |
| 过期证件识别率 | 85%（人工易漏日期） | 100%（规则精确判断） | +18% |
| 安全性 | 100%（人工兜底） | 100%（HITL 兜底） | 不降级 |

**关键：安全性不降级**。这是 HITL 的核心价值——Agent 把 5 分钟压缩到 10 秒，但最终决策仍在人手里。如果全自动审核，一旦 LLM 误判，不合格教练上线 = 安全事故。

### 4.5 面经问答

**Q：证书审核为什么用 HITL 而不是全自动？**

> 三层原因：
> 1. **安全底线**：证书审核是教练上线的最后一道关卡。LLM 误判一个过期证件，不合格教练接单 = 用户安全风险。这是不可接受的风险。
> 2. **法规要求**：健身行业要求"持证上岗"，平台有审核义务。全自动审核无法满足"人工确认"的合规要求。
> 3. **LLM 不可靠**：OCR 可能识别错（"2023" 读成 "2025"），LLM 可能理解错（把"急救证"和"健身教练证"搞混）。HITL 让人做最终判断，Agent 只做提效。
>
> Agent 把 5 分钟压缩到 10 秒（8 秒预处理 + 2 秒确认），80% 人力释放，但 100% 安全兜底。

**追问：HITL 的 interrupt 在 LangGraph 里是怎么实现的？Checkpointer 存什么？**

> interrupt 的本质是"Graph 执行到某节点时暂停，把当前 state 持久化到 Checkpointer，返回 thread_id 给前端；管理员确认后，用 thread_id + 决策结果 resume Graph"。
>
> Checkpointer 存的是整个 Graph 的 state（包含：OCR 提取的证件信息、LLM 的校验结果、建议决策、所有中间变量）。Redis miss 时从 DB 兜底读（防止 Redis TTL 过期导致会话中断）。
>
> 代码层面：`cert_review.py` 的 `hitl_checkpoint` 节点调 `interrupt(value)` 暂停；管理员确认后 API 层调 `Command(resume=decision)` 恢复。Checkpointer 保证了"暂停 → 等人 → 恢复"期间的 state 不丢。

**Q：如果管理员 2 小时后才来确认，Redis state 过期了怎么办？**

> 这就是为什么 Checkpointer 要加 DB 兜底层（[session_store.py](../app/core/session_store.py)）：
> 1. **Redis 是主存**：TTL 60 分钟，读取时续期（活跃 thread 不会被清）
> 2. **DB 是灾备**：aput 时异步双写 DB，TTL = Redis TTL × 2（120 分钟）
> 3. **Redis miss → DB 兜底**：aget miss 时从 DB 读 state → 回填 Redis → 继续会话
> 4. **防雪崩/穿透/击穿**：TTL 抖动 + 空值缓存 + singleflight
>
> 这样管理员 2 小时后来确认，即使 Redis state 过期了，也能从 DB 恢复，不会"审核单找不到"。

**Q：OCR 识别错了怎么办？Agent 怎么处理 OCR 错误？**

> 3 层防护：
> 1. **OCR 置信度**：阿里云 OCR 返回置信度 < 0.8 时，Agent 标记"OCR 不确定，请人工核对"
> 2. **LLM 校验**：LLM 拿到 OCR 结果后做常识校验——证件编号格式对不对？有效期是否在合理范围（不能是 1990 年）？
> 3. **HITL 兜底**：管理员看到的是 OCR 原文 + LLM 校验结果 + 原始图片，可以对照图片人工确认。Agent 不做最终决策。
>
> 最坏情况：OCR 把"2023-12-31"识别成"2025-12-31"（过期变有效）。LLM 校验时如果证件号格式正确、有效期合理，可能识别不出来。所以 HITL 是必须的——管理员看图片原件能发现这个问题，Agent 不能替代。

## 5. 技术选型场景

> 以下每个选型都按"为什么选 X 而不选 Y"的对比结构展开。

### 5.1 为什么选 LangGraph 而不是 LangChain Chain / AutoGen

**场景**：三个 Agent 需要不同的执行范式（DAG / Plan-Execute / ReAct+HITL），且需要 HITL + Checkpointer + 多 Agent 调度。

| 维度 | LangChain Chain | AutoGen | **LangGraph** |
|---|---|---|---|
| 执行模型 | 线性链（A→B→C） | 对话式（Agent 间多轮对话） | **图（StateGraph，支持循环/分支/HITL）** |
| HITL 支持 | ❌ 无 | ❌ 弱 | **✅ interrupt + Checkpointer** |
| 状态管理 | 无状态 / 手动传 | 对话历史 | **Checkpointer（Redis + DB 兜底）** |
| 多 Agent 调度 | 不支持 | ✅ 对话式 | **✅ Supervisor 模式** |
| 适合本项目 | ❌ 无法做 HITL | ⚠️ 偏对话式，控制流不精确 | **✅ 图拓扑精确控制** |

**面试回答**：
> 选 LangGraph 是因为证书审核需要 HITL（暂停等管理员确认），只有 LangGraph 原生支持 `interrupt` + Checkpointer。LangChain Chain 是线性链无法暂停；AutoGen 偏对话式多 Agent，控制流不精确（无法精确控制"OCR → 校验 → 暂停 → 入库"的节点顺序）。LangGraph 的 StateGraph 能精确定义图拓扑，同时支持循环（refine）和分支（校验通过/拒绝），是三个 Agent 的最大公约数。

### 5.2 为什么选 Supervisor 而不是 Handoff

详见 [09-Agent面试题集.md Q1.1](./09-Agent面试题集.md) 的完整对比表。核心 3 条：

1. **任务边界清晰**：三个 Agent 各管一摊（推荐/摘要/审核），不需要控制权转移
2. **Supervisor 能兜底**：子 Agent 失败时 Supervisor 重路由；Handoff 后源 Agent 退出无法兜底
3. **多轮对话需要全局 state**：用户"推荐教练 → 追问评价"需要 Supervisor 持有上下文；Handoff 需要再 handoff 回来，链路复杂

### 5.3 为什么选 RAG 混合检索（BM25 + 向量 + SQL）而不是纯向量

> 注：当前落地只跑 BM25 单路，向量/SQL 召回是目标方案（见 §0.1）。本节讲的是「选型理由」，回答时先说清现状。

| 场景 | 纯向量 | BM25 + 向量 + SQL |
|---|---|---|
| "产后恢复" 找 "盆底肌修复" | ✅ 语义匹配 | ✅ 向量路 |
| "朝阳区" 精确匹配 | ❌ 可能召回"朝阳公园" | ✅ SQL 硬过滤 |
| "预算 200 内" 数值约束 | ❌ 无法精确过滤 | ✅ SQL 范围查询 |
| "李教练" 低频词 | ❌ 召回差 | ✅ BM25 精确匹配 |

**面试回答**：
> 纯向量召回在语义泛化上强，但在精确词、数值约束、低频词上有盲区。混合检索三路互补：BM25 解决精确词 / 向量解决语义泛化 / SQL 解决硬约束（价格/区域/时段）。RRF 融合后 Recall@10 从单路 52% 提升到 78%。详见 [04-RAG混合检索.md](./04-RAG混合检索.md)。

### 5.4 为什么选 Milvus

> 注：代码已选型 **Milvus**，但运行时尚未部署（pymilvus 未装则降级 BM25 单路，见 §0.1）。回答时表述为「我选 Milvus，pymilvus 未装则降级 BM25」而非「我已跑了 Milvus 召回」。

| 维度 | 单机/嵌入式向量库 | **Milvus**（本项目生产） |
|---|---|---|
| 多副本共享 | ❌ 本地文件，副本独立 | ✅ 多副本连同一实例 |
| HA | ❌ 单节点 | ✅ 分布式 + failover |
| 运维工具 | ❌ 无 | ✅ Attu / Prometheus / Grafana |
| HNSW + COSINE | ✅ | ✅ ms 级召回 |
| 分布式扩展 | ❌ | ✅ 水平扩容 |

**面试回答**：
> 单机/嵌入式向量库是本地文件存储，多副本各自一份，A 副本写入 B 副本读不到。Milvus 是分布式向量库，多副本共享同一实例 + HA + HNSW ms 级召回 + 运维成熟（Attu/Prometheus/Grafana）。本地用 `docker run -d --name milvus -p 19530:19530 milvusdb/milvus:latest` 或接 Zilliz 云。配置 MILVUS_URI/MILVUS_TOKEN/MILVUS_DATABASE/MILVUS_COLLECTION/MILVUS_DIM；pymilvus 未装则降级 BM25 单路。详见 [04-RAG混合检索.md](./04-RAG混合检索.md)。

### 5.5 为什么 Checkpointer 要 DB 兜底

详见 [10-上线检查清单.md §1.4.7-1.4.13](./10-上线检查清单.md)。核心痛点：

> Redis TTL 60 分钟，但管理员可能 2 小时后才来确认证书审核。Redis state 过期 → Checkpointer miss → 会话中断 → 审核单找不到。
>
> 方案：Redis 主存 + DB 灾备双写，Redis miss 时从 DB 读 → 回填 Redis → 继续会话。防雪崩（TTL 抖动）+ 防穿透（空值缓存）+ 防击穿（singleflight）。

## 6. 工程化场景

### 6.1 为什么需要 Loop 工程

**场景**：教练推荐的 refine 循环、评价摘要的 self_refine 循环、证书审核的 OCR 重试循环。

| 循环类型 | 场景 | 终止条件 | 代码 |
|---|---|---|---|
| **条件分支** | 证书校验通过/拒绝 | 校验结果 | [cert_review.py](../app/graphs/cert_review.py) |
| **重试循环** | OCR 失败重试 | 最多 3 次 | cert_review OCR 节点 |
| **Refine 循环** | 推荐理由质量不达标 | 质量分 ≥ 70 或 2 轮 | [recommend_coach.py](../app/graphs/recommend_coach.py) |
| **HITL 循环** | 管理员确认/打回 | 人工决策 | cert_review interrupt |

详见 [03-循环工程.md](./03-循环工程.md)。

### 6.2 为什么需要 Memory 系统

**场景**：用户第二次来推荐教练时，Agent 应该记得上次偏好（减脂 + 预算 200 + 女教练）。

| 记忆类型 | 存什么 | 存哪里 | 本项目用在哪 |
|---|---|---|---|
| **短期记忆** | 当前对话 state | Checkpointer（Redis） | 多轮对话上下文 |
| **长期-情景** | 用户历史偏好 | 向量库（Milvus，目标选型） | recommend_coach 个性化 |
| **长期-情景** | 评价历史摘要 | 向量库（目标选型） | review_summary 对比 |
| **长期-程序** | 审核规则 | 规则库 | cert_review 规则校验 |

详见 [02-Agent工程能力地图.md](./02-Agent工程能力地图.md)。

### 6.3 为什么需要 MCP 工具层

**场景**：AI 服务需要调 Spring Boot 后端的"查教练详情"接口，但两个服务用不同语言（Python vs Java）。

MCP（Model Context Protocol）让 AI 服务通过标准化协议调用后端工具，不需要硬编码 HTTP 调用。详见 [07-MCP工具层.md](./07-MCP工具层.md)。

## 7. 上线场景

### 7.1 灰度发布策略

```
阶段 1（5%）：低峰时段 14:00，开 5% 流量，跑 30 分钟
  → TP99 < 3s 且错误率 < 1% → 进阶段 2

阶段 2（20%）：正常时段，开 20%，跑 2 小时
  → 召回率 ≥ 70% 且 HITL 完成率 = 100% → 进阶段 3

阶段 3（50%）：高峰时段，开 50%，跑 4 小时
  → 无 P0 告警 → 进阶段 4

阶段 4（100%）：全量，24h 值守
  → 72h 无 P0/P1 → 上线完成
```

### 7.2 监控告警

| 指标 | 阈值 | 告警级别 | 处置 |
|---|---|---|---|
| TP99 延迟 | > 3s | P2 | 扩容 / 降级 |
| 错误率 | > 1% | P1 | 回滚 |
| 召回率 | < 60% | P2 | 检查向量库 |
| HITL 审核单积压 | > 50 单 | P3 | 加管理员 |
| LLM 调用失败率 | > 5% | P1 | 切换 LLM 供应商 |
| Redis Checkpointer miss | > 10% | P2 | 检查 TTL + DB 兜底 |

### 7.3 回滚预案

触发条件（任一即回滚）：
1. 错误率 > 5%
2. TP99 > 5s 持续 5 分钟
3. LLM 供应商故障
4. 向量库不可用

回滚步骤：
1. K8s `kubectl rollout undo` 回退到上一镜像
2. Redis `FLUSHDB` 清理脏 state（可选）
3. 通知管理员人工接管审核
4. Post-mortem 分析根因

详见 [10-上线检查清单.md](./10-上线检查清单.md)。

> **回答**（30 秒版）：

> 3. **证书审核 Agent**：规则核验 + HITL 人工确认。Agent 做预处理（字段抽取 + 编号/有效期/姓名规则校验），管理员做最终决策，安全性不降级。
>
> 技术栈：LangGraph + Redis Checkpointer（带 DB 兜底防 TTL 过期）+ 可选 Supervisor 多 Agent 调度。目标方案会接 Milvus + Cross-Encoder 精排。"
