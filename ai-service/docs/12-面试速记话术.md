## 一、项目介绍（30 秒开场）

🟢 **"讲讲你的 Agent 项目"**

> 我做了一个**上门体育平台的 AI 微服务**，核心是三个 Agent：
>
> 1. **教练推荐 Agent**：用户说自然语言"生完孩子 3 个月想恢复，预算 200"，Agent 用 LLM 意图抽取 + 混合检索（BM25）+ 5 维规则打分，返回 Top 3 教练 + 推荐理由。做了离线 Eval 基建，95% 通过率、63 单测全绿。
> 2. **评价摘要 Agent**：Plan-and-Execute 结构（规划分批 → Map 打标签 → Reduce 聚合 → 质量门控重写），自动生成优缺点摘要 + 标签。
> 3. **证书审核 Agent**：规则核验 + HITL 人工确认。Agent 做预处理（字段抽取 + 编号/有效期/姓名校验），管理员做最终决策，**安全性不降级**——Agent 提效，人类兜底。
>
> 技术栈：**LangGraph + Redis Checkpointer（带 DB 兜底）+ 可选 Supervisor 路由**。Milvus 向量库已选型（pymilvus 未装降级 BM25），目标方案接 Cross-Encoder 精排。

## 二、多 Agent 通信（09-Q1）

🟢 **Q1.1 多 Agent 协作有哪些模式？**

> 有 **Supervisor、Handoff、Swarm、Debate** 四种。我的三个 Agent 当前是**独立端点**（各走各的 API），架构上预留了 **Supervisor** 路由位——一个主管 Agent 识别意图后派给子 Agent，子 Agent 干完返回。**控制权始终在 Supervisor 手里**。
>
> 对比 **Handoff**：Handoff 是控制权转移——A 把上下文交接给 B，A 退出，B 接管。像客服转接。
>
> 我选 Supervisor（而非 Handoff）的原因：三个 Agent 任务边界清晰，不需要控制权转移；Supervisor 能做全局兜底，Handoff 后源 Agent 退出无法兜底。

🟡 **Q1.3 如何防止死循环？**

> 三道防线：
> 1. **硬性计数器**：意图抽取重试最多 3 次、放宽过滤最多 3 轮、理由重写最多 2 轮，超过即终止
> 2. **LangGraph recursion_limit 兜底**：图级硬上限，超了强制中断
> 3. **质量门控**：理由/摘要为空或超长 → 带反馈重写，重写耗尽回退 mock 模板
>
> 终止后还要**清理资源**：DB 连接池 dispose + Redis 连接池 close（生命周期 finally 兜底）。多 Agent 深度协作的锁清理（LockRegistry）是「用到再建」的进阶能力，当前三个独立端点没有锁场景。

🔴 **Q1.4 Supervisor 单点怎么办？**

> 三级降级链（[supervisor.py](../app/graphs/supervisor.py)）：
> 1. **关键词规则**：mock/离线时用正则匹配意图，0 token
> 2. **LLM 路由**：真实模式下用便宜模型分类，失败降级
> 3. **默认路由**：全挂了走 recommend_coach（最高频场景）
>
> 目标方案会加一层「路由结果缓存」（Redis 命中免 LLM）。Supervisor 默认关闭，三个 Agent 走独立端点，所以「单点」目前不是瓶颈。

## 三、RAG 工程（09-Q2 + 11-§2）

🟢 **Q2.1 什么是 RAG？为什么不用 fine-tuning？**

> RAG 是**检索增强生成**——先从知识库检索相关文档，再喂给 LLM 生成回答。
>
> 不用 fine-tuning 的原因：
> 1. **知识更新快**：教练信息每周变，fine-tuning 要重新训练，RAG 只改向量库
> 2. **成本高**：fine-tuning 要 GPU + 标注数据，RAG 只需 embedding
> 3. **可解释**：RAG 能说"推荐基于这些文档"，fine-tuning 是黑盒

🟢 **（灵魂拷问）为什么不直接多项筛选？**

> **先承认**：如果用户能精确选标签 + 拖滑块，传统筛选够用，不需要 Agent。
>
> 但 Agent 解决的是筛选**做不到**的事：
> 1. **意图→标签翻译**：用户说"生完孩子 3 个月"，不知道该选"盆底肌修复"标签
> 2. **隐含约束推导**：用户说"膝盖不好想减脂"，不会主动说"排除跑步"
> 3. **多轮追问**：用户只说"减脂"没说预算，Agent 主动追问
> 4. **个性化记忆**：第二次来记得上次偏好
> 5. **推荐理由**：不只给列表，还告诉"为什么推荐这个"
>
> 核心认知：**传统筛选解决"用户知道要什么"，Agent 解决"用户说不清要什么"。**

🟢 **Top N 的 N 怎么定？用 top-k 吗？**

> 不是一个 top-k，是**多阶段漏斗式**（当前落地版）：
>
> 1. **SQL 硬过滤** → 全量（城市/等级/评分/性别）
> 2. **混合召回** → BM25 召回（向量/重排是预留接口，当前单路）
> 3. **5 维规则打分** → 评分40/匹配35/等级10/距离10/档期5 加权排序
> 4. **最终返回** → top 3（可配置）
>
> 返回 3 不是 5：手机一屏展示 3 个卡片，重决策场景用户会仔细看前 3 个。目标方案会加 Cross-Encoder 精排（召回 30 → 精排 5 → 取 3），数据量上千教练时再接。
>
> **每个 k 都是召回率、延迟、用户体验三角平衡的结果。**

🟡 **Q2.2 分片策略怎么选？怎么防止分片出错导致理解偏移？**

> 通用首选 **递归分片**（先段落→再句子→再字符）。但分片会切断关键信息——"不适合"和"高血压患者"被切开 → Agent 把禁忌课程推荐给禁忌人群。
>
> **5 层防护**（这是目标设计，见 [09 Q2.2](./09-Agent面试题集.md)，当前 RAG 分片入库管道未落地、依赖未上的向量库）：
> 1. **SafeSplitter**：片尾落在"不/限/元"等禁词就合并下一片
> 2. **元数据保留**：每片带 doc_id + chunk_idx，召回后能拼回
> 3. **父子分片**：召回用小片（150 token 精准），喂 LLM 用大片（500 token 完整）
> 4. **上下文拼装**：同文档按 chunk_idx 拼回，跨文档用分隔符
> 5. **质量校验**：入库前跑断裂/指代/否定孤立检测
>
> 核心认知：**分片让召回变小了，但上下文也变残缺了——召回是缩小镜头，但不能把镜头切到只剩半张脸。**

🟡 **Q2.3 为什么混合检索比纯向量好？**

> 纯向量有三个盲区：
> 1. **精确词不敏感**："朝阳区"可能召回"朝阳公园附近"
> 2. **数值约束不精确**：预算 200 元，向量无法精确过滤
> 3. **低频词召回差**："李教练"匹配不到
>
> 三路互补：**BM25 解决精确词 / 向量解决语义泛化 / SQL 解决硬约束**。（当前落地只跑 BM25 单路，向量/重排是预留接口。）

🟡 **RRF 怎么融合？为什么不取并集？**

> 取并集有两个问题：分数不可比（BM25 是 0~∞，向量是 0~1）+ 排序无依据。
>
> RRF **不看分数只看排名**：`score = 1/(k + rank)`，k=60。两路结果按排名反比融合，天然解决量纲问题。选 RRF 是因为不需要调权重，冷启动更稳。

🟡 **Q2.5 向量库选型：为什么选 Milvus？**

> 本项目已选型 **Milvus**（pymilvus 未装则降级 BM25 单路）。选它而非 Chroma 的原因：
>
> Chroma 的 PersistentClient 是**本地文件**，多副本各自一份，A 副本写入 B 副本读不到。
>
> Milvus 是独立分布式服务：**多副本共享同一实例 + HA + HNSW ms 级召回 + 运维成熟（Attu/Prometheus）**。
>
> 单后端，配置 `MILVUS_URI` / `MILVUS_TOKEN` / `MILVUS_DATABASE` / `MILVUS_COLLECTION` / `MILVUS_DIM`（见 [vectorstore.py](../app/clients/vectorstore.py)）。

## 四、记忆系统（09-Q3）

🟢 **Q3.1 短期记忆和长期记忆存什么？**

> **短期记忆**：当前对话的 state（用户意图、已推荐教练、refine 轮次）。存 Checkpointer（Redis，TTL 60 分钟 + DB 兜底），已落地。
>
> **长期记忆**分三种（当前是目标设计，无向量库）：
> - **情景记忆**：用户历史偏好（约过减脂、偏好女教练、预算 200）→ 向量库
> - **情景记忆**：评价历史摘要 → 向量库
> - **程序记忆**：审核规则 → 规则库（这个已落地，确定性规则硬编码在 [cert_review.py](../app/graphs/cert_review.py)）

🟡 **Q3.2 对话历史太长怎么办？**

> 三步（通用方案，本项目三个 Agent 都是单轮任务、不累积长对话）：
> 1. **滑动窗口**：只保留最近 10 轮原文
> 2. **摘要压缩**：前 10 轮用 LLM 生成 `_summary` 字段
> 3. **长期抽取**：从摘要里抽取关键偏好写入向量库
>
> 超过 20 轮触发压缩，保证 Checkpointer state 不膨胀。

🔴 **Checkpointer 为什么要 DB 兜底？**

> 痛点：Redis TTL 60 分钟，但管理员可能 2 小时后才来确认证书审核 → Redis state 过期 → 会话中断。
>
> 方案：**Redis 主存 + DB 灾备双写**。aget miss 时从 DB 读 → 回填 Redis → 继续会话。
>
> 防雪崩（TTL ±10% 抖动）+ 防穿透（空值缓存 60s）+ 防击穿（singleflight 互斥锁）。

## 五、工具调用（09-Q4）

🟢 **Q4.1 ReAct 和 Function Calling 的区别？**

> **ReAct** 是"思考-行动-观察"循环——LLM 先输出 Thought（推理），再调工具，拿结果后继续推理。适合**多步推理**场景。
>
> **Function Calling** 是 LLM 直接输出结构化函数调用，不需要显式推理。适合**单步执行**场景。
>
> 我的教练推荐用 **Function Calling**（LLM 结构化抽取意图，单步）。证书审核当前是**确定性规则核验**（编号格式/有效期/姓名），ReAct 工具循环留了位、目标方案会接。

🟡 **Q4.3 工具调用错误怎么处理？**

> 四级：
> 1. **重试**：网络抖动，指数退避，最多 3 次
> 2. **降级**：OCR 失败 → 标记"请人工核对"
> 3. **熔断**：连续失败 5 次 → 熔断 30s
> 4. **兜底**：全挂了返回缓存结果或默认值

## 六、Agent 范式（09-Q5）

🟢 **Q5.1 ReAct / Plan-and-Execute / ToT 怎么选？**

> 看任务复杂度：
> - **ReAct**：单链路多步推理（探索性任务，本项目证书审核预留了 ReAct 位）
> - **Plan-and-Execute**：先规划再执行（评价摘要：先分批→打标签→聚合）
> - **ToT**：需要探索多条路径（本项目没用——教练推荐路径确定，不需要树搜索）
>
> 我的三个 Agent：推荐用 DAG、摘要用 Plan-and-Execute、审核用规则核验 + HITL（ReAct 是预留位）。

🟡 **Q5.3 Agent 失败时怎么避免循环重试？**

> 三个终止条件：
> 1. **质量分达标**：refine 质量分 ≥ 70 即停
> 2. **轮次上限**：最多 2 轮（边际收益递减 + Token 成本）
> 3. **重复检测**：连续 2 次输出相同 → 判定卡死
>
> 兜底：2 轮不达标直接返回当前最优结果，不无限循环。

## 七、HITL 人工介入（09-Q6）

🟢 **Q6.1 HITL 怎么实现？interrupt 的本质？**

> interrupt 的本质是**Graph 执行到某节点时暂停，state 持久化到 Checkpointer，返回 thread_id 给前端**。管理员确认后用 `Command(resume=decision)` 恢复。
>
> 我用在证书审核：OCR + LLM 校验后 interrupt，等管理员点"确认/拒绝"，resume 后执行入库或拒绝。

🟢 **证书审核为什么用 HITL 不全自动？**

> 三个原因：
> 1. **安全底线**：证书审核是教练上线最后一关，LLM 误判过期证件 = 不合格教练接单 = 用户安全风险
> 2. **法规要求**：健身行业持证上岗，平台有审核义务
> 3. **LLM 不可靠**：OCR 可能识别错（"2023"→"2025"），LLM 可能理解错
>
> **Agent 做预处理（秒级），管理员做最终决策，人类兜底（安全性不降级）。**

🟡 **管理员 2 小时后才来，Redis state 过期怎么办？**

> Redis TTL 60 分钟，但管理员可能 2 小时后才确认。方案是 **Checkpointer DB 兜底**：
>
> 1. Redis 是主存，TTL 60 分钟 + refresh_on_read（活跃 thread 续期）
> 2. DB 是灾备，aput 时异步双写，TTL = Redis × 2
> 3. Redis miss → DB 读 → 回填 Redis → 继续会话
> 4. 防雪崩（TTL 抖动）+ 防穿透（空值缓存）+ 防击穿（singleflight）

## 八、评估与安全（09-Q7 + Q8）

🟢 **Q7.1 Agent 的 Eval 和单元测试有什么区别？**

> 单元测试验证**代码逻辑**（函数输入输出对不对）。Eval 验证**端到端效果**（推荐质量好不好）。
>
> 我的评估（已落地，[runner.py](../app/eval/runner.py)）：**Intent 准确率 + TopK 命中 + 理由质量分** 三类指标，离线 mock 跑出 19/20（95%）。Recall@10、LLM-as-Judge、在线点击率是目标指标，待真实标注数据 + 上线后回流。

🟡 **Q8.1 Prompt 注入怎么防？**

> 四层防御：
> 1. **输入消毒**：过滤 `<system>` / `ignore previous` 等指令性文本
> 2. **角色隔离**：用户输入放在 `user` 消息，不放 `system`
> 3. **输出校验**：LLM 输出必须符合 Pydantic schema，不符即拒绝
> 4. **工具分级**：READ/WRITE/DANGEROUS 三级，危险操作强制 HITL

🟡 **Q8.2 Token 预算怎么设计？**

> 三级分级（[token_budget.py](../app/middleware/token_budget.py)，已落地）：
> - **单请求预算**：输入 token 上限 10000，超了拒绝
> - **用户日预算**：单用户单日 10 万 token，超了拦截
> - **全局预算**：全局单日 100 万 token，超了拒绝
>
> 用 Redis 计数器实现，**fail-open**（Redis 挂了直接放过，不让保护组件拖垮主链路）。

## 九、部署运维（09-Q9 + Q10）

🟡 **Q9.1 Agent 服务为什么必须异步化？**

> LLM 调用是 IO 密集型（等 API 响应 1-3s）。同步阻塞 → worker 被占满 → 服务雪崩。
>
> 异步方案：FastAPI + `ainvoke` + DB 走 `asyncio.to_thread`（同步驱动不阻塞 event loop）。单 worker 扛多路并发。

🟡 **Q9.2 限流 / 熔断 / 降级有什么区别？**

> | 机制 | 触发 | 作用 |
> |---|---|---|
> | **限流** | QPS > 阈值 | 保护服务不被压垮 |
> | **熔断** | 错误率 > 50% | 保护下游（LLM API）不被打挂 |
> | **降级** | 熔断触发后 | 返回缓存/默认值，不让用户看到 500 |

🔴 **Q10.1 LLM Agent 慢的主因？**

> 三块（当前落地版）：
> 1. **LLM 调用**（占比最大）：意图抽取 + 理由生成各 1 次 = 1-2s
> 2. **BM25 召回 + 5 维规则打分**：纯 Python 离线，百毫秒级
> 3. **DB 查询**：教练/课程/档期（`asyncio.to_thread` 异步）100-200ms
>
> 优化：**流式输出**（SSE）让用户先看到第一个字 + **缓存**高频查询（24h）+ **减少 LLM 调用**（5 维规则打分替代 LLM 精排，Node2 不调 LLM）。

## 十、场景面经（11 精华）

🟢 **评价摘要为什么用 Plan-and-Execute 不直接扔给 LLM？**

> 两个限制：
> 1. **Context window**：87 条 × 150 token = 13K token，Lost in the Middle 问题导致中间评价被忽略
> 2. **质量下降**：一次性处理太多，LLM 只总结开头结尾
>
> Plan-and-Execute 结构：plan 取评价 → map 打标签（当前规则单循环，目标换 LLM 并行）→ reduce 聚合 → reflect 质量门控。每批内容少质量高。

🟡 **Reflection 自评可靠吗？**

> 不可靠，所以当前用**规则门控**（非 LLM 自评）：
> 1. **规则前置**：摘要必须非空 + 长度 ≤ 200 字，不满足直接重写
> 2. **目标方案再加 LLM 打分**：4 维度各 25 分（数据/覆盖/标签/可操作性）
> 3. **兜底**：2 轮不达标返回当前结果，不无限循环

🟡 **OCR 识别错了怎么办？**

> 三层防护（当前 OCR 是 mock 透传，真实 OCR 是目标设计）：
> 1. **OCR 置信度** < 0.8 → 标记"请人工核对"
> 2. **规则校验**：编号格式正则 + 有效期 + 姓名长度
> 3. **HITL 兜底**：管理员看原图 + 校验结果对照，Agent 不做最终决策

## 十一、技术选型速记

🟢 **为什么选 LangGraph？**

> 三个原因：
> 1. 证书审核需要 **HITL**（interrupt + Checkpointer），LangChain Chain 不支持暂停
> 2. 状态管理需要 **Checkpointer**（Redis + DB 兜底）
> 3. 图拓扑精确控制（循环 + 分支 + HITL），AutoGen 偏对话式控制流不精确

🟢 **为什么选 Supervisor 不选 Handoff？**

> 三个原因：
> 1. **任务边界清晰**：三个 Agent 各管一摊，不需要控制权转移
> 2. **Supervisor 能兜底**：子 Agent 失败重路由，Handoff 后源 Agent 退出无法兜底
> 3. **多轮对话需要全局 state**：Supervisor 持有上下文，Handoff 需要再转回来

🟢 **为什么选 Milvus 不选 Chroma？**

> 本项目已选型 Milvus（pymilvus 未装则降级 BM25 单路）。
> Chroma PersistentClient 是**本地文件**，多副本不共享。
> Milvus 是独立分布式服务：**多副本共享同一实例 + HA + HNSW ms 级召回 + 运维成熟（Attu/Prometheus）**。
> 单后端，配置 `MILVUS_URI` 等（见 [vectorstore.py](../app/clients/vectorstore.py)）。

## 十二、面试一页纸（终极背诵版）

> "我的项目是上门体育平台的 AI 微服务，三个 Agent：
>
> 1. 教练推荐——用户说自然语言，LLM 意图抽取 + BM25 混合检索 + 5 维规则打分，离线 Eval 95% 通过率
> 2. 评价摘要——Plan-and-Execute 结构（分批 → 打标签 → 聚合 → 质量门控重写）
> 3. 证书审核——规则核验 + HITL，Agent 预处理 + 管理员兜底，安全性不降级
>
> 技术选型：LangGraph（图+循环+HITL）+ Redis Checkpointer（DB 兜底防 TTL 过期）+ 可选 Supervisor 路由。Milvus 向量库已选型（pymilvus 未装降级 BM25），目标方案接 Cross-Encoder 精排。
>
> 核心认知：**传统筛选解决'用户知道要什么'，Agent 解决'用户说不清要什么'。** 上 Agent 不是替代筛选，是补筛选做不到的——意图翻译、隐含约束推导、多轮追问、个性化记忆、推荐理由。"
