## 0. 文档说明

### 0.1 目标

把当前 `recommend_coach` 从「固定 3 节点串行 DAG」升级为「带 4 类循环控制的状态机」：

1. **条件分支**：Node2 候选为空 → 回 Node1 放宽条件重抽
2. **重试循环**：Node1 LLM 抽 JSON 失败 → 累加修正提示重试 N 次
3. **Refine 循环**：Node3 推荐理由质量门控不合格 → 回 Node3 重写
4. **HITL 人工介入**：预留一个 `interrupt` 节点，为后续证书审核 Agent 铺路

### 0.2 范围与边界

| 项 | 是否改动 | 说明 |
|---|---|---|
| 对外 HTTP 契约（输入/输出 JSON） | ❌ 不动 | 向后兼容，旧前端/Java 后端无感 |
| Pydantic Schema 输出 | ❌ 不动 | `RecommendResult` 字段不变（新增字段为可选） |
| Graph 内部 State 字段 | ✅ 新增 | retry_count / relaxed_fields / quality_check 等 |
| 节点函数实现 | ✅ 重构 | 抽出"宽松度参数" + "质量门控函数" |
| 编译方式 | ✅ 改 | 挂 `RedisCheckpointer` + thread_id |
| 部署配置 | ✅ 改 | `.env` 加 `CHECKPOINT_TTL` / `MAX_RETRIES` / `QUALITY_MIN_SCORE` |

## 1. 现状回顾

### 1.1 当前 Graph 拓扑

```
START → extract_intent → retrieve_and_rank → generate_reason → END
```

特点：
- 纯串行，**无任何分支/循环**
- [base.py](../app/graphs/base.py) 写了 `ConditionalRouter` 但 `recommend_coach.py` **未调用 `add_conditional_edges`**
- 节点失败立即 fallback mock，**无重试**
- Node2 候选为空时硬塞 mock 教练，**无回退抽取**
- Node3 推荐理由无论质量都直接返回，**无门控**
- 无 Checkpointer，**进程崩了无法 resume**

### 1.2 四大缺口清单

| 缺口 | 触发条件 | 当前行为 | 期望行为 |
|---|---|---|---|
| G1 条件分支 | Node2 `filtered` 为空 | 硬塞 `_MOCK_COACHES` | 回 Node1 放宽条件（去掉 city / 降低 level）重抽，最多重试 2 次 |
| G2 重试循环 | Node1 LLM 返回非 JSON | 立即抛 RuntimeError | 累加修正提示重试 N 次（默认 2），仍失败才 fallback mock |
| G3 Refine 循环 | Node3 推荐理由不合格 | 直接返回 | 回 Node3 重写（带"上次输出 X，问题 Y"提示），最多重试 2 次 |
| G4 HITL | 预留 | 无 | 通过 `interrupt()` 暴露人工介入点（教练推荐本身不需要，但为后续证书审核 Agent 跑通基础设施） |

## 2. 设计思路：为什么这样设计而不是那样

### 2.1 为什么用 ConditionalRouter 而不是 if-else

LangGraph 中实现分支有三种方式，对比：

| 方式 | 代码 | 可读性 | 可观测性 | 推荐 |
|---|---|---|---|---|
| 节点内 if-else + 多入口 END | 节点函数里写分支逻辑 | 差 | 差（看不到分支） | ❌ |
| 节点返回下一节点名 | `return {"next": "node_a"}` | 中 | 中 | ⚠️ |
| **ConditionalRouter + add_conditional_edges** | 路由表声明式 | 好 | 好（拓扑图清晰） | ✅ |

**关键认知**：Graph 的拓扑结构应当**显式声明**而非藏在节点函数里。这样：
- Trace 工具能画出真实走向
- 改路由不需要改节点函数
- 新人看拓扑就能理解流程

### 2.2 为什么"先重试再 fallback mock"

当前实现是「LLM 失败立即 mock」，问题：
- 偶发性失败（网络抖动 / 模型抽风）也走 mock，质量降级
- 无日志区分"模型真挂了" vs "模型偶发抖动"

正确顺序：
```
LLM 调用失败
   ↓
重试 N 次（带退避 + 修正提示）  ←—— 区分偶发 vs 必败
   ↓ 仍失败
fallback mock + 日志告警       ←—— 必败才降级
```

### 2.3 为什么 Refine 用"质量门控函数"而不是"LLM 自评"

Refine 循环触发有两种方式：

| 方式 | 实现 | 成本 | 准确度 |
|---|---|---|---|
| LLM 自评（"你觉得这个理由好吗"） | 多一次 LLM 调用 | 高 | 中（LLM 评自己有偏好） |
| **规则门控函数**（长度/含数据/无空话） | 纯 Python 函数 | 0 | 高（规则明确） |

**原则**：能用规则判定的，绝不浪费 LLM。规则门控通过后才考虑 LLM 自评（更高阶场景）。

### 2.4 为什么教练推荐不需要 HITL 但仍要预留

HITL 不是为了教练推荐本身，而是为了**让 LangGraph 的 interrupt + Checkpointer 基础设施在本项目跑通**。后续证书审核 Agent 必须用 HITL（管理员最终确认）。

如果 Phase 1 不把这套基础设施跑通，Phase 5 写证书审核 Agent 时要同时解决「业务逻辑 + HITL 工程」两个问题，风险叠加。**先用工具有效的低风险场景跑通基础设施，再上高价值场景**——这是工程化的标准做法。

### 3.1 缺口 G1：条件分支（Node2 空结果回 Node1 放宽）

#### 3.1.1 状态字段设计

在 `RecommendState` 新增字段：

#### 3.1.2 放宽策略函数

按"代价从低到高"顺序放宽（先放宽便宜的字段，后放宽贵的）：

```python
# app/graphs/recommend_coach.py 新增
_RELAX_ORDER: list[tuple[str, str]] = [
    # (字段名, 放宽动作描述)
    ("min_rating", "去掉最低评分限制"),
    ("level", "去掉教练等级限制"),
    ("male_only", "去掉性别限制"),
    ("district", "去掉区域限制，仅保留城市"),
    ("city_name", "去掉城市限制，全国兜底"),
]


def _relax_intent(intent: dict, relaxed_fields: list[str]) -> tuple[dict, list[str], str | None]:
    """按顺序放宽一个未放宽过的字段。返回 (新intent, 新relaxed_fields, 放宽动作名/None)"""
    for field, action in _RELAX_ORDER:
        if field in relaxed_fields:
            continue
        if intent.get(field) is None:
            continue  # 本来就没限制，不用放宽
        new_intent = {**intent, field: None}
        new_relaxed = relaxed_fields + [field]
        return new_intent, new_relaxed, action
    return intent, relaxed_fields, None  # 全放宽完了
```

在节点末尾根据 `filtered` 是否为空 + `retry_count` 决定写 `branch`：

### 3.2 缺口 G2：重试循环（Node1 LLM 抽 JSON 失败重试）

#### 3.2.1 设计思路

LLM 抽 JSON 失败有三种情况：
1. **网络/超时**：偶发，立即重试就好
2. **格式错误**（多了 ```json 标记、字段名漂移）：重试时带"上次输出 X，错误是 Y，请按 schema 重新输出"提示
3. **schema 必填字段缺失**：重试时强调缺失字段

LiteLLM 内置的 `num_retries` 只处理第 1 种（HTTP 重试），第 2/3 种要业务层自己实现。

#### 3.2.2 代码骨架

```python
# app/clients/llm.py 新增


def chat_structured_with_retry(
    messages: Iterable[dict[str, str]],
    output_schema: Type[T],
    max_retries: int = 2,
) -> tuple[T, list[dict]]:
    """带修正提示重试的结构化输出。返回 (结果, 全部尝试的 messages 记录)。"""
    all_messages = list(messages)
    last_exc: Exception | None = None

    for attempt in range(max_retries + 1):
        try:
            result = chat_structured(all_messages, output_schema)
            return result, all_messages
        except (RuntimeError, ValidationError) as exc:
            last_exc = exc
            if attempt == max_retries:
                break
            # 关键：累加修正提示，让 LLM 看到自己的错误
            correction = (
                f"你上次的输出有问题：{exc!s}\n"
                f"请严格按 JSON Schema 重新输出，不要包含任何 markdown 或多余字符。"
            )
            all_messages = all_messages + [{"role": "user", "content": correction}]
            logger.warning("[chat_structured] 第 %d 次失败，重试：%s", attempt + 1, exc)

    raise last_exc  # 重试耗尽，抛给上层走 fallback
```

### 3.3 缺口 G3：Refine 循环（Node3 推荐理由质量门控）

#### 3.3.1 质量门控函数

```python
# app/graphs/recommend_coach.py 新增

_EMPTY_WORDS = ("很专业", "很棒", "非常好", "推荐", "优秀", "靠谱", "值得")


def _check_reason_quality(reason: str, candidates: list[dict]) -> tuple[bool, str]:
    """返回 (是否合格, 不合格原因)。合格标准：
    1. 长度 30~200 字
    2. 至少点出 2 位教练的差异化卖点（含教练名）
    3. 不含空泛词
    """
    if not reason or len(reason) < 30:
        return False, "理由过短（<30 字），缺乏信息量"
    if len(reason) > 200:
        return False, "理由过长（>200 字），需要精简"
    names_in_reason = sum(1 for c in candidates if c.get("name", "") in reason)
    if names_in_reason < 2 and len(candidates) >= 2:
        return False, "未点出至少 2 位教练的差异化"
    if any(w in reason for w in _EMPTY_WORDS) and names_in_reason < 2:
        return False, "含空泛词且无具体数据支撑"
    return True, ""
```

### 3.4 缺口 G4：HITL（人工介入预留点）

#### 3.4.1 设计思路

教练推荐**本身不需要人工审核**——它是纯算法决策，自动化即可。但为了：
1. 给后续证书审核 Agent 跑通 `interrupt + Checkpointer` 基础设施
2. 应对"高价值订单人工确认"潜在场景（如月销 > 50 单的 VIP 客户推荐金牌教练时，可加一个运营复核点）

预留一个**可选启用**的 HITL 节点。默认关闭，配置开关 `HITL_ENABLED=false`。

#### 3.4.2 LangGraph interrupt 用法

```python
# app/graphs/recommend_coach.py 新增

from langgraph.types import interrupt, Command


def hitl_checkpoint(state: RecommendState) -> dict[str, Any]:
    """HITL 检查点：暂停等待人工确认推荐结果。
    默认不启用；启用后通过 graph.invoke(..., config={"configurable": {"thread_id": ...}})
    配合 interrupt + Command(resume=...) 完成。
    """
    candidates = state.get("candidates") or []
    if not candidates:
        return {"branch": "done"}

    # interrupt 会暂停 Graph，state 持久化到 Checkpointer
    # 人工可通过外部 API 调用 Command(resume={"approved": True/False}) 恢复
    human_decision = interrupt(
        {
            "prompt": "请确认是否启用这批教练推荐",
            "candidates": [c.get("name") for c in candidates[:3]],
            "user_query": state.get("user_query"),
        }
    )

    if not human_decision.get("approved"):
        # 人工拒绝 → 回 Node1 重新生成（带 feedback）
        return {
            "branch": "relax",
            "retry_count": int(state.get("retry_count", 0)) + 1,
            "reason_feedback": "人工拒绝了这批候选",
        }
    return {"branch": "done"}
```

## 4. Checkpointer 接入

### 4.1 为什么必须接

| 场景 | 无 Checkpointer | 有 Checkpointer |
|---|---|---|
| 进程崩了 | 整次推荐丢失，用户重试 | 从最后一个 checkpoint resume |
| 多副本部署 | thread_id 无意义，状态不一致 | thread_id 路由到 Redis，多副本共享 |
| HITL interrupt | 暂停后状态丢失，无法 resume | 暂停即持久化，等数小时也能恢复 |
| 调试 | 无法回放 | time travel 到任意 checkpoint |

## 8. 关键设计决策回顾

| 决策点 | 选项 | 选择 | 理由 |
|---|---|---|---|
| 分支实现方式 | if-else / ConditionalRouter | ConditionalRouter | 拓扑显式声明，可观测 |
| 重试触发 | LiteLLM 内置 / 业务层 | 业务层 | 内置只处理 HTTP，不处理格式错误 |
| Refine 触发 | LLM 自评 / 规则门控 | 规则门控 | 节省 LLM 调用，规则明确 |
| HITL 启用方式 | 默认开 / 默认关 | 默认关 | 教练推荐本身不需要，开关控制 |
| Checkpointer 介质 | Memory / Redis / Postgres | Redis（生产）+ Memory（开发） | Redis 多副本共享 + TTL 自动清理 |
| thread_id 来源 | UUID / user_id | user_id（默认） + UUID（匿名） | 同用户多次推荐状态可关联 |
| 放宽策略 | 一次性全放宽 / 按序逐个 | 按序逐个 | 保留尽量多硬过滤，提升精度 |

## 10. 学习要点小结

读完这份文档，你应该掌握：

1. **Graph 拓扑应当显式声明**，不要藏在节点函数里 → 用 `add_conditional_edges + ConditionalRouter`
2. **重试与 fallback 分层**：HTTP 重试（LiteLLM 内置）→ 业务重试（带修正提示）→ mock 兜底，三层职责清晰
3. **能用规则就不用 LLM**：质量门控用 Python 函数，不用 LLM 自评
4. **基础设施先于业务跑通**：HITL 在不需要的场景先预留，等真用时不慌
5. **状态字段设计是 Loop 工程的核心**：`retry_count` / `relaxed_fields` / `branch` 三个字段决定了循环怎么走
